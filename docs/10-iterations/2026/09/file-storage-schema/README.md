# `file-storage-schema`｜MinIO 文件元数据表

## 这次迭代解决什么问题

本次迭代为文件上传建立数据库元数据模型。`app_file` 记录用户归属、业务类型、Bucket、Object Key、文件校验信息和上传生命周期，使 MinIO 对象能够被业务安全地确认、预览和删除。

## 范围与边界

- 包含 V2 Migration、用户头像外键、文件状态、业务类型和幂等键设计。
- 数据库只保存稳定的 Bucket/Object Key，不保存永久 URL 或永久签名 URL。
- 头像归属用户；账单附件必须同时归属账本和账单，但相关业务表尚未生成时不提前制造跨表外键。
- 上传授权、确认、预览 URL、删除清理和归属校验代码不属于本次纯 Schema 迭代；后续 H5/MinIO 迭代再实现。

## 文件怎么读

`01` 定义文件能力和非目标；`02` 解释对象与元数据的关系及安全决策；`03` 对照 V2 Migration 和字段；`04` 列出未来 API；`05`、`06` 标明后端和前端尚未实现的部分；`07` 是文件状态、幂等和越权用例；`08`、`09` 分别记录命令和验证证据；`10` 描述 Migration 尚未执行与已进入共享环境后的回滚原则。

## 当前使用注意

即使后续代码已实现头像链路，也不能据此宣称账单附件已开放。`AVATAR` 与 `TRANSACTION_ATTACHMENT` 的业务边界、文件归属和 MinIO 清理策略必须分别验证。
