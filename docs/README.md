# 文档中心

本目录是哈记账项目的设计、实现约束、验证证据和历史变更档案中心。文档的目的不是单独描述“页面长什么样”，而是把需求、数据库、API、前后端实现、权限、测试、构建和运行验证串成可追溯链路。

## 先看哪里

| 目标 | 入口 | 说明 |
| --- | --- | --- |
| 了解项目与首版边界 | [`00-overview/`](00-overview/) | 产品范围、术语、首版开放与未开放能力。 |
| 了解系统如何分层 | [`01-architecture/`](01-architecture/) | 后端分域、前端分层、数据流和跨模块约束。 |
| 设计或审查数据库 | [`02-database/`](02-database/) | 表分类、公共审计字段、金额、删除和 Flyway 规则。 |
| 设计或审查接口 | [`03-api/`](03-api/) | API 契约、认证、归属校验、错误和幂等要求。 |
| 开发前端页面 | [`04-frontend/`](04-frontend/) | uni-app 页面、状态、API 入口、平台差异和交互验收。 |
| 启动、部署和排障 | [`05-operations/`](05-operations/) | 环境、依赖、配置、日志、运行和回滚操作。 |
| 做安全审查 | [`06-security/`](06-security/) | 身份认证、权限、IDOR、文件、密钥和敏感信息保护。 |
| 编写或执行测试 | [`07-testing/`](07-testing/) | 测试分层、数据准备、构建和联调证据。 |
| 核对设计稿与实现 | [`08-design/`](08-design/) | 原型、视觉稿和实际页面的验收关系。 |
| 查看阶段验收结论 | [`09-audit/`](09-audit/) | PASS、PARTIAL、FAIL、BLOCKED、NOT_RUN 的证据记录。 |
| 了解某次具体改动 | [`10-iterations/`](10-iterations/) | 按日期和 feature-key 保存变更档案及回滚信息。 |

## 文档层级与权威性

- `00-overview` 至 `08-design` 是当前规范区。这里的规则用于指导新代码和新文档；发生变化时应直接更新对应规范，并在迭代档案中记录原因。
- `09-audit` 是证据区。它记录某一阶段实际执行过的检查，不等同于目标清单；没有命令、输出、截图或代码定位等证据时，只能写 `NOT_RUN` 或 `BLOCKED`。
- `10-iterations` 是历史区。它按 `YYYY/MM/feature-key` 保存一次需求的完整闭环，历史记录不能因为后来实现变化而被静默改写。
- 正式数据库结构以 `server/src/main/resources/db/migration/` 为准；文档中的数据库说明必须与 Flyway、`information_schema` 和 Entity 一起核对。

## 迭代档案的固定阅读顺序

每个完整迭代目录按以下顺序阅读：`01-requirement`（为什么做）→ `02-design`（怎么设计）→ `03-database`（数据变化）→ `04-api`（协议变化）→ `05-backend`（后端实现）→ `06-frontend`（前端实现）→ `07-testing`（如何验证）→ `08-commands`（实际执行了什么）→ `09-verification`（结论）→ `10-rollback`（如何撤回）。目录 README 负责给出该迭代的摘要和导航。

部分早期迭代在当前工作区只有 README，表示该目录的历史明细尚未恢复或尚未补齐；不能据此推断功能已经实现。

## 状态词含义

| 状态 | 含义 |
| --- | --- |
| `PASS` | 已执行，并且结果符合预期。 |
| `PARTIAL` | 只完成了部分范围，剩余范围必须明确写出。 |
| `FAIL` | 已执行但结果不符合预期。 |
| `BLOCKED` | 因真实外部依赖不可得而无法执行。 |
| `NOT_RUN` | 尚未执行，不能当作通过。 |

## 文档维护要求

新增重大功能、Bug、数据库、权限、基础设施或设计整改时，先在 `10-iterations` 建档，再修改代码；完成后同步规范区、审计矩阵和第三轮审计。命令记录必须来自真实执行，且不得包含密码、Token、AppSecret、Access Key 或永久签名 URL。
